# M4.11.1 威胁模型与功能边界

本步只交付威胁模型与边界，**不实现加密**。当前私聊仍是服务端明文，界面必须写「尚未端到端加密」。

## 功能边界

| 范围 | 约定 |
| --- | --- |
| 第一阶段加密对象 | 仅**双向已接受好友**之间的 1:1 私聊（文本；媒体/附件须用独立内容密钥，见 M4.11.4） |
| 群聊 | **暂不承诺 E2EE**。在实现并审查前，界面不得暗示群聊已加密。 |
| 公开内容 | 动态、评论、社区帖、通知正文、个人资料 **不在** E2EE 范围，服务器可见。 |
| 元数据 | 即使将来有 E2EE，服务器仍可能看到会话双方、时间、消息大小、投递状态。不把“元数据不可见”写成已实现。 |
| 搜索 | 当前明文私聊会被服务端搜索索引。E2EE 接入后，**密文不得进入服务端索引**（已在 M4.7 注明）。 |
| 举报（M4.8 / M3.5） | 管理端默认不可浏览私聊。仅当用户主动举报并提交其勾选的 `messageIds` 时，才可查看这些消息及必要上下文，并写审计。E2EE 落地后，应由用户在客户端解密后随举报表单提交明文副本，而不是给管理员一把能打开全部历史的密钥。 |
| VIP | E2EE 不是付费功能，不得做成「付费更安全」。 |

## 当前实际威胁（E2EE 未实现时，必须对用户诚实）

- **服务器运营者或拿到数据库的人可以阅读全部私聊明文。**
- 传输层有 HTTPS（部署正确的前提下），只保护「到服务器」这一段，不是端到端。
- 访问令牌存在 `localStorage`（Bearer）。页面 XSS 可以盗用会话并读取该账号可见的消息。Cookie 方案交 M6.1，不在本步改。
- 推送预览、日志、备份若包含正文，也会泄漏明文。实现方不得把私聊正文写进普通日志。

## 目标威胁模型（将来正式 E2EE 时要对抗的对象）

1. **网络窃听者：** 不能从传输中读出消息内容（TLS 已覆盖到服务器；E2EE 覆盖端到端）。
2. **恶意或被攻破的服务器：** 只能看到密文和元数据，不能解密内容，也不能默默降级为明文而不被客户端察觉。
3. **恶意管理员：** 默认看不到私聊；只在用户提交的举报范围内看用户交出的内容，并留审计。
4. **设备丢失：** 私钥只存在客户端安全存储；丢失设备上的密钥应能被用户撤销。能否恢复历史，取决于密钥恢复方案（见下，负责人决定）。
5. **恶意联系人：** E2EE 不防止对方向外转发明文；安全号码/身份指纹只证明「正在和哪把密钥说话」。
6. **被篡改的 Web 客户端：** 单文件 HTML 由服务器下发。被替换的脚本可以在加密前把明文送走。Web 端 E2EE 必须单独评估客户端完整性，不能假装“有库就安全”。

不在本模型承诺范围内：国家级对抗、侧信道、用户自己的截屏/转发、已经泄露的旧明文备份。

## 设备数量与密钥恢复（留给负责人）

这两项调研提出选项，**本步不擅自选定、不实现**。

- **设备数量：** 每台设备应有独立设备密钥。建议对同时在线的已验证设备设上限（例如 5～10 台），超过则需撤销一台再加入。具体上限由负责人决定。
- **密钥恢复：**
  - **不提供云端恢复：** 丢失全部设备即无法解密历史。最不易扩大服务器信任面。
  - **用户保管的恢复密钥 / 助记词：** 用户责任大，产品要写清风险。
  - **加密云备份（用户口令包裹）：** 便利，但口令强度和服务器上的密文备份成为新的攻击面；不得做「服务器可解开」的备份。
- **新设备加入：** 必须经已有设备确认或等效安全验证，不能只靠登录密码就自动拿到全部历史密钥。

## 本步不做什么

不生成设备密钥，不改消息格式，不安装协议库，不把「威胁模型已写」说成「已经端到端加密」。
