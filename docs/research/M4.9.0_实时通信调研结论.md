# M4.9.0 实时通信调研结论

依据：`docs/research/NOVA_V7_调研报告_M2.3_M4.9_M4.11_M5.1_M6.4.md`（调研基准日 2026-11-12）第 4 节，以及本仓库已实现的 M4.3.4 SSE。本步把结论固化为开发约定，不重复展开来源考证。

## 结论（已采纳，写入实现）

1. **第一阶段继续 SSE + POST。** 服务端用 `GET /api/events`（`text/event-stream`）单向推送；客户端发消息仍走普通 `POST`。对当前规模（本人和朋友、新消息与通知）足够。
2. **鉴权只用 `Authorization` 头，禁止把访问令牌放进 URL。** 浏览器原生 `EventSource` 不能自定义请求头，因此客户端用 `fetch()` 读流，并经 `apiUrl()` 拼接 `window.NOVA_API_BASE`（空则同源）。查询参数出现 `token` / `access_token` / `auth` / `authorization` 时服务端返回 400 `TOKEN_IN_URL`。
3. **升级 WebSocket 的条件（须同时或明确满足再评估，见 M4.9.2）：**
   - 在线状态、输入中等需要高频双向推送；或
   - 实测证明 SSE + POST 的延迟/请求量已成为瓶颈；或
   - 需要更复杂的实时协作或持续双向同步。
4. **升级时必须补齐：** 连接鉴权、心跳、断线重连、消息确认、去重、离线补拉、连接限流、服务端关闭、横向扩展广播、自动化测试。Node.js 22 的 `http.Server` 只有 `upgrade` 事件，**没有内置 WebSocket 服务端**；若升级须选用受维护的库（候选见 M4.9.2），并继续遵守 CORS 白名单与 `NOVA_API_BASE`。
5. **会话改为 HttpOnly Cookie** 属于 M6.1 安全评估，本步不临时把令牌拼进 URL，也不提前改会话方案。

## 留给负责人的决定

- **何时真正升级 WebSocket：** 上述条件是否已被产品需求或压测触发，由负责人决定。本版本默认不迁移。
- **会话载体：** 继续 Bearer Token（`localStorage`）还是改为 HttpOnly Cookie（需配套 CSRF），交 M6.1 与负责人，不在 M4.9 改动。

## 本步不做什么

不引入 WebSocket 依赖，不把现有 SSE 换成双向套接字，不把令牌放入查询参数。
