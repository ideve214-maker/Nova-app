# M4.11.4 私聊加密/解密、密文传输与媒体密钥（待办）

**状态：待办，本步不实现。** 原因同 M4.11.2 / M4.11.3：没有可投入生产的协议库。保持服务端明文存储，界面标明尚未端到端加密。**禁止**把现有正文用 AES 等自制方案包一层当作密文。

## 选定库并完成审查、设备密钥就绪之后，必须满足

1. **服务端只路由密文。** 消息内容、附件明文不以可读形式写入数据库、日志、审计、推送预览或搜索索引。
2. **客户端加密后再 POST，解密后再展示。** 传输层仍走现有 HTTPS + `POST /api/conversations/:id/messages`（或其后继），载荷为协议库规定的密文结构，不是自拟 JSON 包。
3. **媒体/附件：** 使用内容密钥加密文件本身；服务器保存密文 blob。内容密钥随消息密钥保护，不单独明文存服务端。
4. **当前已遵守的一条（明文阶段也适用）：** `chat.message` 审计只记录 `messageId`，不记录正文。将来密文阶段继续不得把明文写入审计。
5. 群聊不在本阶段承诺。降级攻击（对端或服务器要求改回明文）必须被客户端拒绝并提示用户。

## 当前实现

- `messages.text` 为发送者提交的明文。
- `GET` 历史原样返回明文。
- M4.7 搜索会检索用户可见的明文私聊；E2EE 接入后密文不得进入该索引。

## 本步不做什么

不改消息表结构冒充密文，不自写加解密，不把「待办已写」说成已加密。
