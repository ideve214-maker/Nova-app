# M4.11.4 私聊加密/解密、密文传输与媒体密钥

**状态：已实现（1:1 文本）。** 客户端用 vodozemac（Olm）加密后再 POST；服务端只保存和路由密文，不解密。禁止用自制 AES 包装冒充协议。

## 已实现

1. **服务端只路由密文。** `POST /api/conversations/:id/messages` 在 `encrypted: true` 时要求 `ciphertext` 为 `{v:1, envelopes:[{deviceId, type, body}]}`（body 为 vodozemac 产出的 Olm 预密钥/普通密文）。`messages.text` 对加密消息固定为空。夹带明文或在信封里放 `text`/`plaintext` 会被拒绝。
2. **客户端加密后再 POST，解密后再展示。** 对端用 inbound session（预密钥消息）或已有 session 解密。本机发出的消息用本地明文缓存展示（Olm 会话不能用来解自己刚发出的密文）。
3. **降级防护：** 客户端对 1:1 私聊在对端有密钥时始终加密；对端没有密钥时拒绝发送并提示，不改为明文。群聊请求加密会 400 `E2EE_GROUP`。
4. **搜索：** 加密消息不进入服务端明文索引（`encrypted=1` 且 text 为空）。
5. **举报：** 管理端看到的加密消息正文为空；用户可在客户端把解密副本作为 `messageCopies` 提交，服务端标记为用户提交的副本，不当作自己解开的明文。
6. **审计：** `chat.message` 只记录 `messageId`，不记录正文或密文。
7. **群聊**仍为明文，界面标明暂不加密。

## 限制

- **媒体/附件内容密钥：** 文本已走 Olm。附件用内容密钥封装文件、再把密钥放入 Olm 消息的完整路径尚未作为默认发送路径落地；加密私聊中请以文字为主。这不是用 AES 冒充 E2EE。
- 旧的明文私聊记录仍按原样保存和展示；新的用户端 1:1 发送走密文。服务端为兼容既有测试与群聊，仍接受明文 POST，但用户端不会在私聊里主动降级。

## 本步不做什么

不自写加解密算法；不用 AES 把明文包一层当作「已加密」；不把群聊假装成已加密。
