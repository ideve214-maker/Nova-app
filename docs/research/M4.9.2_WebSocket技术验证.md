# M4.9.2 WebSocket 技术验证（本步不迁移）

依据 M4.9.0 结论：当前没有「在线状态 / 输入中」等双向高频需求，也没有 SSE+POST 成为瓶颈的实测，**本步只做技术验证，不把传输从 SSE 换成 WebSocket**。

## 1. 服务端库候选

Node.js 22 的 `http.Server` 仅提供 `upgrade` 事件，**没有内置 WebSocket 服务端**。若将来升级，候选如下（调研基准 2026-11-12，实施前须再核对官网与许可证）：

| 库 | 许可证（调研时） | 维护情况 | 说明 |
|---|---|---|---|
| [`ws`](https://github.com/websockets/ws) | MIT | 广泛使用、持续维护 | 最常见的 Node 服务端选择；可挂到已有 `http.Server` 的 `upgrade`。 |
| [`undici`](https://github.com/nodejs/undici) WebSocket | MIT | Node 官方 HTTP 客户端 | 主要是**客户端**；不能替代服务端库。 |
| 自写帧解析 | — | — | **不采用**：容易在掩码、分片、关闭握手和扩展上出错。 |

建议：若升级，首选 `ws`（MIT，与零依赖策略冲突，须在 `package.json` 显式加入并锁定版本，写入 `THIRD_PARTY_NOTICES`）。**本仓库此刻不安装该依赖**，以免在未决定迁移时打破「后端零依赖」约定。

## 2. 必须验证（升级时的验收清单，均未在本步实施）

1. **鉴权**：握手阶段用 `Authorization` 头（或同源 HttpOnly Cookie，见 M6.1），**禁止**把访问令牌放在 URL 或 Sec-WebSocket 子协议里当密钥。与 SSE 同一套会话。拒绝未登录、令牌过期。跨域时 CORS 不适用握手，须单独校验 Origin（复用 `NOVA_CORS_ORIGIN` 白名单）。
2. **心跳**：服务端定期 ping、客户端 pong；超时断开；与现有 `: ping` 语义对应。
3. **断线重连**：客户端指数退避；重连后带最后事件 id / 消息游标。
4. **消息确认**：应用层确认或至少幂等 `clientId`（已有）；不能假装「已送达」。
5. **断线补拉**：复用 `chat_events` 与 `GET .../messages?after=`，不另搞一套会丢事件的缓冲。
6. **连接限额**：与 SSE 同样按用户限流（默认 4），超额明确错误。
7. **`NOVA_API_BASE`**：客户端连接地址必须经同一基址（`wss://` 对应 `https://` API 源），不能写死相对路径导致 Capacitor 打到壳的本地源。
8. **关闭与横向扩展**：服务端重启要踢掉连接；多进程时需广播方案（本阶段单进程 SQLite，记录即可）。

## 3. 验证结果（本环境）

- 本环境**可以**联网安装依赖，但按照 M4.9.0 与「零依赖后端」约定，**不在本步安装 `ws`，不开放 WebSocket 端口，不迁移现有客户端**。
- 现网传输仍是：`fetch(apiUrl('/api/events'))` + `POST` 消息；`GET /api/events` 的 `Content-Type` 为 `text/event-stream`。
- 迁移标记为**待办**，触发条件见 M4.9.0（负责人决定何时升级）。
