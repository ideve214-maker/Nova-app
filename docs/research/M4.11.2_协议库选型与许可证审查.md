# M4.11.2 协议库选型、维护状态与许可证审查

依据：M4.11.0 结论与调研报告第 5 节。本步完成**审查**，**不选定、不安装**生产用库。不自创算法。

## 审查标准（必须同时满足才可进入实现）

1. 实现成熟协议（Signal 体系或 MLS 等），不是作者自创的“类 Signal”包装。
2. 有明确的维护者、发布渠道和版本策略；API 稳定性可评估。
3. 官方或维护者支持在 Signal 产品之外（或等价产品之外）的使用，而不是“仅供本产品、外部自担风险”。
4. 许可证与 NOVA 的发布方式相容；若为 AGPL 等强互惠许可，须由**负责人书面接受**或取得商业许可后再用。
5. 能覆盖计划中的客户端：当前 Web（单 HTML / 浏览器），并预留后续 iOS 等；有可行的密钥存储接口。
6. 单独使用该库不能被宣传为“已经 E2EE”；还须完成设备管理、降级防护、审查和 UI 诚实标识（见 M4.11.3–5）。

## 审查对象

### libsignal（Signal 官方）

- **协议：** 配套 X3DH / PQXDH、Double Ratchet 等，适合作为 1:1 研究对象。
- **接口：** 官方仓库提供 Java、Swift、TypeScript 等绑定。来源：[libsignal](https://github.com/signalapp/libsignal)、[Signal 技术文档](https://signal.org/docs/)。
- **许可证（调研基准日 2026-11-12）：** 仓库以 **AGPLv3** 发布。引入后可能对整体发布义务产生影响，必须由负责人决定是否接受，或另行洽谈商业许可。本仓库**不擅自引入**。
- **支持范围：** 仓库明确说明，**在 Signal 产品之外使用不受支持**，接口和实现可能变化。对“本人和朋友使用的 Web 应用”来说，这不是可直接投入生产的依赖。
- **结论：不采用（至少在支持政策、许可证和 API 稳定性满足标准之前）。不安装。**

### MLS 实现

- **协议：** IETF RFC 9420 / RFC 9750，更适合**未来群组**评估。第一阶段是 1:1，不需要先上 MLS。
- **实现：** 本步不挑选、不引入任何 MLS 库。群聊暂不承诺 E2EE。

### 自制或“只用 Web Crypto AES”

- **不采用，且禁止。** 用 AES-GCM 包装明文、自写 ratchet 或自拟握手，都不是本项目允许的 E2EE。依赖装不上或许可证谈不拢时，正确做法是保持未加密并标明待办。

## 结论

**尚未选定可直接投入生产的协议库。** 本仓库 `package.json` 不添加、`node_modules` 不安装 libsignal 或其它 E2EE 聊天库。M4.11.3 / M4.11.4 在选定库并完成审查之前只交付待办说明，不写加密实现。

## 留给负责人的决定

- 是否接受 AGPLv3，或为 libsignal（或其它候选）取得商业许可。
- 是否等待官方对“产品外使用”给出可接受的支持政策后再评估。
- 是否把 1:1 私聊 E2EE 推迟到有满足上述六条标准的库之后（推荐：是）。

## 本步不做什么

不安装依赖，不改许可证，不写密钥与密文代码，不把本审查文件当作已加密的证明。
