# M4.11.0 私聊 E2EE 技术调研结论

依据：`docs/research/NOVA_V7_调研报告_M2.3_M4.9_M4.11_M5.1_M6.4.md`（调研基准日 2026-11-12）第 5 节。本步把结论固化为开发约定，不把“读过某份协议”或“安装某个库”当作加密已完成。

## 结论（已采纳）

1. **端到端加密（E2EE）不是 HTTPS。** HTTPS/TLS 只保护客户端到服务器的传输通道；当前 NOVA 私聊消息在服务端以明文存储和转发，运营者或攻破服务器的人可以阅读内容。E2EE 的目标是：消息在发送端加密，只有收件端能解密，服务器只传递密文。
2. **第一阶段目标仅为双向好友之间的 1:1 私聊 E2EE。** 群聊暂不承诺、不做、也不在界面上暗示已加密。将来群组方向可评估 IETF MLS（RFC 9420 / RFC 9750），不在本阶段实施。
3. **禁止自创算法。** 不得自行实现密钥交换、Double Ratchet、随机数、签名或加密封装，也不得用 `crypto.subtle` / `node:crypto` 的 AES 简单包装来冒充 Signal/MLS 级别的 E2EE。
4. **本步尚未选定可直接投入生产的协议库。** Signal 官方 [libsignal](https://github.com/signalapp/libsignal) 提供 TypeScript 等接口，但仓库明确：**在 Signal 产品之外使用不受支持**，API 可能变化，当前以 **AGPLv3** 发布。它不是“装上就自动获得完整安全聊天”的组件。本仓库**不安装** libsignal，也不引入任何加密聊天依赖。
5. **装上库也不等于 E2EE 已完成。** 还需要身份绑定、密钥轮换、多设备、离线消息、重放/降级防护、附件加密、备份恢复、以及 Web 客户端完整性（单 HTML 由服务器下发，被篡改的客户端可以悄悄关掉加密）。
6. **上线门槛：** 协议库及许可证审查、跨设备测试、独立安全审查、威胁模型和界面说明均通过后，才能把界面从「尚未端到端加密」改为「已端到端加密」。在此之前必须保持诚实标识。

## 协议方向（研究，非实现）

- **Signal 体系：** X3DH / PQXDH 与 Double Ratchet，适合作为 1:1 私聊的研究对象（前向保密等）。来源：[Signal 技术文档](https://signal.org/docs/)。
- **MLS：** IETF 标准化的群组密钥协议，面向 2 到数千人、支持成员变更，更适合未来群组评估。来源：[RFC 9420](https://www.rfc-editor.org/rfc/rfc9420/)、[RFC 9750](https://www.rfc-editor.org/rfc/rfc9750.html)。
- **libsignal：** 见上文许可与“不受支持”限制。[仓库](https://github.com/signalapp/libsignal)。

## 留给负责人的决定

- **是否接受 AGPLv3（或另行取得商业许可）才能使用 libsignal。** 这会影响整个产品的许可证义务，必须由负责人决定，本步不擅自引入。
- **何时选定生产用库：** 在 Web/PWA 与后续 iOS 的平台支持、维护频率、版本升级和许可证都核验之前，不选定、不安装。
- **独立安全审查的安排**（谁审查、何时），见后续 M4.11.5，通过前不得改界面文案。

## 本步不做什么

不安装 libsignal 或任何 E2EE 依赖；不改消息存储；不把现有明文包装成“密文”；不把 UI 改成已加密。
